# Changelog

## [0.4.0+session.19] - Unreleased

- New setting `drop_open_turn_thinking` (bool, default off). When it is on, a session native spawned cold in the middle of a turn (a compaction commit lands as one) replays that unfinished turn without its thinking blocks (`thinking` and `redacted_thinking`, signatures with them). Its text and tool calls stay. An assistant frame left empty (stream-json carries one block per message) is dropped. Earlier, closed turns are untouched. A rebuild drops only what the native it retires dropped, and only while its replay still starts with exactly the frames that drop saw. The rebuilt native then replays the retired native's rows, and keeps the cache read and session.17's retired-prefix mark. Thinking produced after the drop is kept. Without this, the first rebuild after a drop (rebuild:suffix after a screenshot, say) would rewrite everything from the dropped turn onward. A rebuild with no single retired native (`rebuild:ambiguous`) drops nothing. Each time it applies, the plugin logs `session open-turn thinking dropped: session=<id> blocks=<n> how=<mode>`. Why: after a mid-turn compaction commit, the next user turn sometimes read only the tools+system prefix and rewrote the whole history a second time (300-430k tokens on eva). Probable cause: an open turn that carries thinking, closed by a first answer without thinking. Reproduced once at ~349k (Opus 5.5, synthetic). In eva's logs, both same-native cases fit (11-23 01:39 and 18:38); three older cases were rebuilds and cannot separate the causes. The API mechanism is unproven. Every probe run without thinking in the open turn read the cache in full on the next turn. **The trade:** for the rest of that one turn, Claude loses its own reasoning from before the commit. On adaptive-thinking models it keeps thinking (the probe's open turn without thinking still drew thinking from Opus 5.5). Anthropic's docs say a mid-turn conflict can silently disable thinking for a request; on a route without adaptive thinking that could mean no thinking for the rest of that turn (unverified). A cold spawn mid-turn that is not after a compaction (an evicted, busy-skipped or crashed native) also replays that turn changed. With an open turn longer than about 20 blocks, its next request can then rewrite the whole history, as a cold spawn usually does anyway once the cache has expired. A cold spawn that follows a native which dropped (evicted while its cache was warm, crashed, or a rebuild that fell back to a per-call step) gets no drop record. It replays that turn with its thinking, so it rewrites from that turn onward: the same as with the setting off. Off by default; turned on for eva only, where LCM-X deferring mid-turn commits is expected to make these rare.
- `session cold: session=<id> mode=<step mode> dropped=<blocks|off> n=<k> opens=<user|tool> rows=<n> think=<type>:<display> marks=<s|m row.block:ttl,...> sys=<bytes,...> open_think=<n> closed_think=<n> hist_think=<n> sys_changed=<indexes|none|->` lines. They are logged for a session native's first two requests, and for the first later request that opens a new user turn, where the second write lands. `mode` is that step's session mode (`cold`, `reused`, `rebuild:*`). `dropped` is how many open-turn thinking blocks this native's spawn replayed without: a count on a cold spawn, `again:<n>` on a rebuild repeating its retired native's drop, `off` otherwise. `opens=user` ignores trailing per-request system rows, a request repeated byte for byte (a retry) is not counted again, and a TTL or thinking value outside the known set (`5m`, `1h`, `adaptive`, `enabled`, `disabled`, `summarized`, `omitted`, `updates`) logs as `?`. Marks are listed as forwarded. System blocks are listed by length, and `sys_changed` names the blocks whose bytes differ from that native's previous request. The comparison uses keyed digests (HMAC-SHA256, the parity key), which stay in memory and never reach the log. Thinking blocks are counted in the open turn, in the turn the request closes, and in the whole history. Counts and positions only: never a digest or text. Log only.

## [0.4.0+session.18] - Unreleased

- `session parity:` lines name the first row whose bytes changed, not only the first whose counts changed. Each rebuild line ends in `byte_diff=<row> byte_role=<old/new> byte_block=<index> byte_kinds=<old/new>`, `byte_diff=none` when every row of the retired native's last request is byte-identical, or `byte_diff=-` when no digests were taken. A kept-alive native's once-per-native `self_diff` line carries the same byte field, which names an earlier same-length edit that arrived with the count change; a same-length change the counts cannot see, or one earlier than a later count change after that line, logs `self_bytes rows=<n> byte_diff=...`, up to three times per native (the first may be routine). A role change with identical blocks reads `byte_block=- byte_kinds=-/-`. Rows are compared by keyed per-block digests (HMAC-SHA256 with a per-process key that stays in memory) of each block without its cache mark (and a tool_result's nested blocks without theirs, since marks move between requests); a `cache_control` key inside tool input is data and is compared. A role change counts as a byte change. Key order inside a block counts too: the digest keeps the forwarded order, since Anthropic documents that `tool_use` key order breaks the cache (a restored row in another key order may show up as a change that does not miss). The log carries only row and block indexes, role codes and block kinds from a fixed list (`?` for any other); never a digest, text or key. This is to find what same-length edit leaves some rebuilds, and the occasional reused step, reading only the tools and system prefix; counts-only parity cannot see such an edit. Cost: about 7 ms per 2 MB request on the relay thread. Log only: nothing about marks, reuse, kills or replay changed.
- `session diverged: why=suffix` lines end in `nonstr=<n>`: the tool results in the new suffix whose content is not a string (a screenshot's list content, say). A native answers tool rounds over MCP with text only, so such a round is replayed on a new native by design; the count names that reason on the line.

## [0.4.0+session.17] - Unreleased

- A rebuilt native's first request carries one more cache mark: on the last row of the retired native's last request, when every row of that request is unchanged and more rows follow. That request's cache entry ends there, but the rebuild's request has more rows after it, and its only message mark is at its end. The API looks back only about 20 blocks from a mark, so a long tail rewrote the whole conversation even with every earlier row unchanged: eva's 23:17 rebuild on 11-22 read only the tools+system prefix and wrote ~360k. A live probe (Haiku 5.5, synthetic) with a 31-block tail read 0 and wrote 20,106 without the mark, and read 18,921 and wrote 1,174 with it. The mark copies the next genuine mark in API order (else the one before it), so TTLs stay non-increasing; fields inside tool schemas are never mistaken for marks. The mark sits at a row boundary, not necessarily at the retired entry's exact end: when native or the relay's pinning placed that entry's mark earlier, more than ~20 blocks away, it can still miss; that case is not measured, and should cost about what such a rebuild costs today. It is added only when fewer than 4 marks are present, on the first request of a rebuilt native only, and never on per-call requests. Any failure forwards the request as is. The parity hand-over it reads is still logged as before.

## [0.4.0+session.16] - Unreleased

- A conversation step with reasoning off asks for thinking on at the lowest effort, on every route with adaptive thinking: `thinking: {type: adaptive, display: summarized}` with `output_config.effort: low`, the same thinking parameters as its other turns. It thinks at least that much: on a kept-alive native launched higher, it thinks at the native's effort (next item). `gen=effort:` on the step line is the effort the step asked for, not the native's. Hermes turns reasoning off for single turns of a conversation (its voice-turn route by default, a thinking-only truncation's continuation). Before, such a turn sent no thinking on routes that cannot disable it, so Claude Code sent its own default (`display: updates`), or sent the disable on routes that accept it. Either way the thinking parameters changed for that turn and Anthropic dropped the conversation's message cache, and the next turn changed them back: two full history rewrites per voice note. Auxiliary one-shots (titles, compression and the like) keep the nearest real off as before. Routes without adaptive thinking (Haiku 4.5) keep the disable. The trade: a reasoning-off turn now thinks a little, at low effort.
- Session reuse no longer keys on the effort alone, and it never lowers the effort a step asked for. Claude Code writes its launch effort into its environment row near the top of the conversation: a per-message effort row, sticky for every later turn. So a kept-alive native thinks at its launch effort for life, and a native launched at another effort sends a different conversation prefix, which means a full cache rewrite. One conversation now keeps one native while that native's effort covers the step: a reasoning-off turn (low) or a medium turn reuses a native launched at high and thinks at high. A step that asks for more effort than its native has replays the conversation once on a native launched at the higher effort (`mode=rebuild:effort`), and later lower asks reuse that one. Whether a step names an effort at all still counts, and key order still counts (a schema's property order). Every other generation setting (thinking, format, output cap, stop sequences) still keys the session. New continuity scenarios: S9 (high, off, high, medium, off, high) reuses one native at high on all six turns, with byte-identical prefixes and a constant effort row. S10 starts on an off turn, rebuilds once at turn 2 to high, and then reuses.

## [0.4.0+session.15] - Unreleased

- `session step:` ends in `gen=thinking:<type>,effort:<level>,format:<json|->,max_tokens:<n>,temperature:<v>,top_p:<v>,stops:<count>,ctx_edits:<count>` (`-` when unset; `gen=-` if it cannot be read). These are the generation settings inside `body=`, which key session reuse and, for thinking and effort, decide whether Anthropic keeps the message cache. When `body=` changes between steps of a conversation, `gen=` names the setting that did. Settings only, never message or tool content. Log only: nothing about reuse, kills or replay changed.

## [0.4.0+session.13] - Unreleased

- Session-mode log lines carry more metadata for the cache audit (lengths, counts, enum words and short keyed hashes only, never message text; new fields go at the end of existing lines). `session kill: ... reason=step-failed-or-poisoned` now ends in `why=`, naming every condition that fired, joined by `+`: `refusal`, `denied`, `native-error`, `unparsed`, `not-offered`, `stop-mismatch`; `raised-<ExceptionType>` for a step that raised; `closed` when the caller closed the stream first. Two labelling limits: a poisoned step that later raises logs its condition words, not `raised-<ExceptionType>`, and any other `BaseException` (such as `KeyboardInterrupt`) reads `closed`. `native-rewrote-tool-result` stays its own reason, and other reasons are unchanged. `session step:` ends in `tools= sys= launch= body= model=`, 8-hex digests of the tool list, the system prompt, the launch configuration, the request body (which holds the tool list too) and the model, the parts the session identity hashes, keyed with the same random secret as `session diverged:`. The secret is drawn when the plugin module loads, so digests compare only within one loaded build of the plugin (a plugin reload draws a new one). A digest failure logs `tools=- sys=- launch=- body=- model=-` and never fails the step. Nothing about reuse, kills or replay changed.
- A native started at a tool-result row (a replay after a respawn whose newest row is tool results) now sends that row with the same bytes on every request. On a subscription login, Claude Code appends its account reminder inside that row and keeps it; the relay removed it only while the row was the newest, so from the native's next step on the row went upstream with the reminder, while a successor replays it without. Each such native's later requests and every later replay of that conversation differed there and missed the prompt cache written before it. The relay now remembers that one row: its index, Hermes' frame, and a digest of the row exactly as native sent it on its first request (cache_control aside), which pins both the frame and native's addition. On each later request a pass of its own, after the newest row's restoration (so a mismatch there cannot undo it), cleans that row to the first request's content only when it still equals that sent row (a re-issued first request restores as any newest row does, and the row is recorded again as sent then); that pass never marks a step unrestored, and anything else (other text after the result, an extra block), or any failure in it, goes upstream as native sent it, and the step line ends in `spawn_row_kept=<index>:<now>/<at spawn>:<differs|shape|unmatched|error>`, where the numbers are lengths of the row's ASCII-escaped JSON form (`-` when the row has none) (log only, never a reuse or kill decision). The record (index, Hermes' frame, digest) is released when the native's relay closes, and the outcome is reset each step. Natives spawned at a turn start remember nothing and pay nothing.
- New log-only `session parity:` line, to find the rows a live native sends that a replay does not. Each forwarded request's message rows are profiled after every relay transform (per row a role code, the block count and the characters of its text, thinking and signatures, tool_result text, base64 data and serialized tool_use input; never text or hashes of it), and a native's relay keeps only its latest profile plus, until its first request, the retired native's handed-over one; both are released when it closes, and the hand-over leaves nothing on the session itself. Once per native, when a later request changes a row an earlier request already sent: `session parity: session=... self_diff row=<i> role=<r> blocks=<old>/<new> chars=<old>/<new> rows=<n>`. On a rebuild, only from the one native that checkout retires for it (none when that is ambiguous; when two conversations share the session identity and first answer, the checkout itself cannot tell them apart, so `prev=` is the native it retired), the new native's first request is compared with the retired native's last: `session parity: session=... prev=<old pid> first_diff=<i|none> role=<r> blocks=<old>/<new> chars=<old>/<new> rows=<new>/<old>`. Cold spawns are not linked. Trailing per-request `role: system` rows are dropped on both sides, and a row one side lacks reads `-`. The relay only queues the notes; the session thread logs them with the step line. Any failure skips the line; nothing feeds reuse, kills or replay. Each session-mode request pays one more parse of the forwarded body.

## [0.4.0+session.12] - Unreleased

- New setting `inherit_launch_login` (default off). A profile whose Claude login is the one the Hermes process inherited (the shared `~/.claude`, or the gateway's token) sets it, and its served tasks keep that login under multiplexing: its own cron jobs and Run now, fired in its own gateway (the tests drive core's in-process fire). Not in core's restart-safe cron worker (a managed Linux gateway hands each fire to one): the worker can't show which profile's gateway started it, so there the profile needs a login of its own (tested through core's worker entry). Core has stamped the launch profile's own in-process cron fire with the process home since 2026-10-20, and session.10 began counting any stamped scope as a served profile's, so from session.10 such a profile's own jobs were refused with "This profile has no Claude login of its own" (eva's daily job, 2026-11-18). The setting is read from the served profile's own config and counts only while the Hermes process was started for that profile (its own gateway): the launch profile opting in gives no other profile its login, a backend started for another profile never lends that profile's login to an opted-in profile's job, and only a YAML boolean true counts (quoted strings and numbers are refused). Never set it in a machine-wide managed config, which would apply it to every profile. Setting `claude_config_dir` to `~/.claude` is not a substitute: Claude Code keys its Keychain login by config directory, so an explicit `CLAUDE_CONFIG_DIR=~/.claude` finds no login.

## [0.4.0+session.11] - Unreleased

- A session retired because its conversation diverged (`rebuild:prefix` or `rebuild:suffix`) now logs one `session diverged:` line first; idle, dead, launch-identity and unpaired retirements log none: where the request left the history the session had consumed (`at`, both lengths), the shape of the change (`insert`, `delete`, `replace-one`, `truncated`, `other`), how many overlapping rows differ, the role and changed field at that row, the lengths of the two keys and their common prefix and suffix, and a short hash of each side, keyed with a random per-process secret so a short message can't be recovered from the log by guessing (the two sides still compare within one gateway process). For an unexpected suffix it logs what the session expected and what came. Ids, counts and hashes only, never message text. The comparison already ignores metadata Hermes adds, so every divergence is a change in replayed bytes.

## [0.4.0] - Unreleased

### Added

- `extra_usage_reserve_percent` setting (unset by default): in `ask` and `stop`, a request is refused once the session or weekly plan window reaches that percent and extra usage is on, so the request that would first be billed is never sent; unattended runs (`/goal`, cron) no longer pay one overage request before the policy acts. It reads the zero-inference `get_usage` check and each turn's own `rate_limit_event`. Unset, invalid, 0 or above 100 keeps today's behaviour (#398 item 1, thanks @mister-ideas and @salch-cred).
- `max_concurrent` setting (default 4) caps the Claude Code turn processes one Hermes process runs at once, across subagents, auxiliary calls and the profiles of a multiplexed gateway (#329). A subagent fan-out used to start one process per call at the same moment (about 250 MB each, all on one subscription). A call past the cap waits for a free place within its own timeout instead of failing or falling back; an interrupt ends the wait at once without starting Claude Code; a wait over 2 s is logged. `/usage` and the model picker do not count.
- `max_concurrent` setting (default 4) caps the Claude Code turn processes one Hermes process runs at once, across subagents, auxiliary calls and the profiles of a multiplexed gateway (#329). A subagent fan-out used to start one process per call at the same moment (about 250 MB each, all on one subscription). A call past the cap waits for a free place within its own timeout instead of failing or falling back; an interrupt ends the wait at once without starting Claude Code, and a call whose wait timed out or was interrupted never starts on a slot freed after it gave up (the slot goes to the next waiter); a wait over 2 s is logged. `/usage` and the model picker do not count.
- Organization gateway opt-in (#46): per-profile `upstream_url`, `upstream_proxy` (HTTP CONNECT, credentials in `CLAUDE_SUBSCRIPTION_DIRECTSDK_PROXY_AUTH`) and `upstream_ca_file` settings route every relay (turns, `/usage`, the picker handshake) through the organization's gateway. Claude Code sends only Messages requests to that relay; its own account calls (`/usage`, bootstrap, MCP directory, telemetry when on) go to `api.anthropic.com` and now take the configured proxy and CA too (`HTTPS_PROXY`, `NODE_EXTRA_CA_CERTS` on the child). Any one set is the opt-in; a set but invalid value (including a non-string one such as `upstream_proxy: false`) refuses the request instead of going to Anthropic directly. One warning per profile names the host the Claude login's bearer goes to. An inherited `ANTHROPIC_BASE_URL` stays refused. Supersedes P#257 (thanks @salch-cred), P#130 (thanks @alextidalrise) and P#23 (thanks @MematiBas42), which selected the route from environment variables.
- `extra_usage` setting (`allow`, `notify`, `ask`, `stop`; default `notify`) decides what a request does once Claude Code reports the account is drawing paid extra usage (#43). It reads native's `rate_limit_event` (`isUsingOverage`, `resetsAt`), which the plugin used to drop (P#281, thanks @salch-cred), and keeps the state in memory per process and login; no files are written. `ask` and `stop` refuse before Claude Code starts, with the reset time and the `hermes config set` line that allows it (`extra_usage_allowed_until` in `ask`). A refusal is a plan-limit stop, so Hermes does not switch to a fallback provider. In `ask` and `stop` a check that cannot tell (no usage answer) refuses with its reason instead of sending a possibly paid turn, and the check asks about the turn's own login and route. Supersedes P#282 (thanks @creditlabsonarc-rgb), whose marker file and guessed expiry are replaced by native's own reset time.

### Changed

- Replaying a long history starts one stdin watchdog thread per request instead of one `threading.Timer` thread per frame (602 thread starts for a 300-round history). The plugin's own CPU per call drops by about 45% at 100 and 300 tool rounds (0.42 to 0.23 s at 300 rounds, 4 vCPU Linux, Claude Code 2.1.327 against a loopback upstream). A write that blocks is still killed at its own deadline.
- `claude_code_telemetry` is off by default (#331): every Claude Code child starts with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY` and `DISABLE_ERROR_REPORTING` set unless the setting is turned on, which also takes about 0.25 s off each spawn. The model picker stays complete: its zero-inference `initialize` handshake leaves `DISABLE_TELEMETRY` and the nonessential-traffic flag unset (either one shrinks the CLI picker from 13 rows to 5 on 2.1.319), so it lists the same 12 routes as with telemetry on. A flag you export yourself is kept.

### Fixed

- The plugin keeps working after core's frozen import copy is deleted under a running Hermes (hermes-agent#156493). Since Hermes 0.23 a `$HERMES_HOME` provider plugin is imported from a copy in the process temp directory, which Hermes' scratch pruner (after 24 idle hours, when `TMPDIR` is its scratch directory) or macOS's daily temp cleanup (files older than 3 days) can remove. `create_client` imported the client module on first use, and every tool-bearing turn ran `inert_mcp.py` from the copy, so both failed. The client is now imported with the package, and the helper is read at import and written next to each turn's `tools.json`.
- A `claude` older than 2.1.280 found first on the service PATH (an old npm install in `~/.hermes/node/bin` ahead of `~/.local/bin` in a systemd unit) no longer answers turns: it dropped the tool payload and replies came back as title JSON. When PATH finds an outdated CLI, the plugin uses a supported one from the usual install directories instead; an explicit command or `CLAUDE_SUBSCRIPTION_DIRECTSDK_COMMAND` is never second-guessed, and each binary's `--version` is asked once, not on every turn (#380, thanks @smshd and @salch-cred).
- Parallel auxiliary calls (two `vision_analyze` calls in one step, or several subagents) no longer cancel each other with "Claude request cancelled" / "Claude client is closed". Hermes' auxiliary cache closes a cached client that another live event loop still uses, and `Client.close()` cancelled every request on it. Each request owns and reaps its own Claude Code process, so `close()` now leaves running requests alone and the client keeps accepting new ones; `cancel()` and a stream's own `close()` still stop work (#378, thanks @aatifk and @salch-cred).
- A relay transport failure on an HTTP-200 response that ends early (`UpstreamIdle`, a connection reset) is named in the error with wording Hermes' classifier already matches, so an auxiliary call such as a compaction summary is retried as a connection failure instead of an unknown error that skipped retry, fallback and the compressor's network-failure guard. The wording is core's premature-close kind, which never reads as a context overflow (#396, thanks @CryptoKylan and @salch-cred).
- A delegated child's requests write their prompt cache at 5 minutes, not one hour. Core clamps a child to the 5m tier (`_apply_child_cache_ttl`: a subagent calls every few seconds and is gone, so the 2x write buys retention it never collects), but core can only clamp the markers it builds, and on this route native places them: a `claude -p` turn is Claude Code's main conversation, which asks for one hour on a subscription within plan usage, so every child request paid the 2x write instead of 1.25x. The profile hook reads core's child cache scope (`sub_<hash>`, `prompt_cache_scope.is_sibling_cache_scope`) and the spawn sets `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` for that request (Claude Code 2.1.242+, older ones ignore it); a value you export yourself wins. Interactive and other requests are untouched.
- A relay starts without asking DNS for its own name. `http.server` looked up 127.0.0.1's name (`socket.getfqdn`) on
  every bind, only to fill a field the relay never reads. On a host whose resolver stalls on that lookup the first
  call of each Hermes process waited it out (35 s on one macOS host; later calls hit the resolver's cache).
- A model step's loopback relay closes at once. `close()` used to wait for the relay's `serve_forever` to see the
  shutdown at its next 50 ms poll: up to 50 ms on every step, at the end of the step for a refused or failed one, and
  before the `max_concurrent` slot of a finished one-shot is free. Now the relay's loop wakes on close. Offline
  (`evals/directsdk_relay_close.py`, Claude Code 2.1.292, 2.1.322, 2.1.323): `close()` after a random idle 22.5 to
  22.8 ms -> 0.29 to 0.45 ms median; right after start 50.2 to 50.3 ms -> 0.03 ms; a per-call tool step at `max_concurrent`
  1, which waits for the previous step's slot, 17 to 36 ms faster (median of three runs' medians). A relay that cannot start its loop
  fails at once and closes its listener.
- A call waiting for a `max_concurrent` slot never starts after its own deadline or its cancellation. A slot freed while it
  was between polls used to be taken on waking, so a call that had timed out (or been interrupted) still started
  Claude Code; the slot now goes to the next waiter and the call raises its timeout or cancel error.
- An empty `.oauth_refresh.lock` that a Claude Code left after exiting mid-refresh (anthropics/claude-code#95236) is removed from the child's own login directory before every spawn, once it is past Claude Code's 60 s stale window; before, every request failed with "another Claude Code process is refreshing it" until the user deleted it. A lock with contents or a fresh mtime is never touched (P#25, thanks @LevSky22 and @100yenadmin).
- The picker and `/usage` probes own their Claude Code child: it is killed and waited for before its scratch directory is removed, on every path, and at interpreter exit. `hermes status` on Windows printed a `PermissionError [WinError 32]` traceback, left a `claude-directsdk-picker-*` directory and a running `claude.exe` behind, because the catalog refresh thread was still inside the handshake when Hermes exited (C#146288). A launcher that exits before the CLI it started (a shell or npm shim) no longer leaves that CLI running: probes and turns share one process-group helper that signals the group while the leader is still unreaped.
- Setup no longer reports a Console API key, an API-key helper or a cloud backend login (Bedrock, Vertex, Foundry) as a working subscription login: `claude auth status` says `loggedIn: true` for those too, so setup passed and the first turn failed. It now says which login Claude Code would use and how to switch (P#28, thanks @100yenadmin).
- Claude Code is no longer looked up under a relative `HOME`, which resolved against the current directory and could run a `claude` planted there (P#27, thanks @grantjayy).
- The "Third-party apps now draw from your extra usage" 400 is classified as a billing stop with a message that names the plan settings and the `hermes-agent` caller, instead of an unknown error that core answered silently from a fallback provider (P#296).
- A multiplexed gateway (`gateway.multiplex_profiles: true`) runs each profile's Claude Code on that profile's own login. `CLAUDE_CODE_OAUTH_TOKEN` in a served profile's `.env` now reaches its Claude Code children (read from core's per-turn secret scope; multiplexing never loads it into the process environment). A served profile without a token of its own no longer inherits the gateway process's token, `ANTHROPIC_CUSTOM_HEADERS` or `CLAUDE_CONFIG_DIR`, with or without `claude_config_dir` (Claude Code prefers the token over the selected login directory), so no profile runs on another profile's account. A served profile with neither its own token nor its own config directory is refused with a login error naming both ways to give it one (`claude_config_dir`, or `CLAUDE_CODE_OAUTH_TOKEN` in its `.env`), since Claude Code would otherwise read `~/.claude` under the inherited home. With no secret scope bound, the request and the setup probes fail closed instead of guessing. Single-profile installs and an explicit `Client(env=...)` are unchanged, and the process environment is never modified (#34, #313, thanks @kalfian).
- `/usage` shows the extra-usage state, usage credits spent, this week's share per surface and the per-model limits beside the plan limits. They were dropped whenever Claude Code answered with `limits`, which current versions always do.
- `/usage` shows the plan limits with `claude_code_telemetry: false`: the CLI skips its `get_usage` fetch under `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, so the zero-inference usage probe no longer sets that one flag (telemetry and error reporting stay off; a flag the user exported is kept).

### Fixed

- A used-up plan window now tells Hermes when it reopens: the 429 that rejects it (`anthropic-ratelimit-unified-status: rejected`) carries the window's reset as `body['resets_at']`, from the `anthropic-ratelimit-unified-reset` header native builds its own limit message from. Hermes parses only a relative `resets in 2h 10m`, not that message's clock time (`resets 3:45pm`), so it never knew: a configured fallback benched this provider on a blind 60 s → 4 h backoff, the limit notice named no reset time, and the Desktop error card offered no retry at the reset.
- An Anthropic API key in Hermes' environment (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_FOUNDRY_API_KEY`), set for Hermes' own `anthropic` provider, no longer blocks this provider: it is dropped from every Claude Code child instead of failing the turn (an explicit `Client(env=...)` keeps it, like the other inherited-environment guards), so both providers work from the same Hermes and a subscription turn never bills API usage. Setup and model discovery no longer pass it to `claude auth status` either.
- Preserve the upstream request ID in incomplete-response errors, including an HTTP 200 stream cut short by EOF or a connection reset. Only a bounded, validated ID is added to the error text and metadata, without enabling debug logging or changing retry admission.
- The picker lists the account's own models: models access-gated per account (Mythos 5.1) and older ones it still runs (Opus 4.7, Fable 5) appear exactly when Claude Code offers them. Native serves that catalog only first-party (behind any `ANTHROPIC_BASE_URL` it logs `[servedCatalog] off (not_first_party)` and answers a generic list), so the `initialize` handshake now talks to Anthropic directly; it sends no user turn, so no Messages request. An inherited auth or backend override keeps the handshake behind the relay.
- The Fable usage-credits note follows Anthropic's plan rule for both Fable 5 and 5.1: shown on Pro, not on Max or Ultra (it was shown on Ultra), and on Team/Enterprise worded `usage credits on standard seats`, since the handshake does not name the seat tier and premium seats include Fable.
- The same work uses about 1.7x less of the subscription's 5-hour window: native now runs as `hermes-agent` instead of `claude -p`'s default `sdk-cli`, a name subscriptions meter about 2x heavier per token (anthropics/claude-code#97074; live on Max with Opus 5.5: 12% vs 7% of the window for the same $2.19 of requests). A name inherited from a host (`sdk-py`, `claude-desktop`) is overwritten too, and native's artifact scratchpad line, which a non-SDK name switches on, stays out of every request.
- Claude Code's own context no longer reaches Claude inside the user's message, where Claude took it for a prompt-injection attempt: native's auto memory (`MEMORY.md`) and CLAUDE.md files are not loaded (`--setting-sources ''` left auto memory and the managed CLAUDE.md on), and the relay drops the context native prepends to the conversation's first user turn (the account-email reminder) instead of moving it behind Hermes' frame, matching how every later request replays that turn (#195, thanks @obahareth).
- Claude's reasoning reaches Hermes again: adaptive-thinking requests ask for `thinking.display: "summarized"`, as core's Anthropic adapter does. Claude 4.7 and later default the display to omitted, which returned signed but empty thinking blocks and left the reasoning panel blank (#45, thanks @mister-ideas). A turn of thinking alone, with no text and no tool call, still reaches Hermes without reasoning, so Hermes nudges the model on instead of taking the thinking as the final answer and ending the tool loop (thanks @100yenadmin, @shaggy2626).
- Long tool calls are no longer cancelled as stalls: the relay asks the API to stream each tool's arguments as they are written (`eager_input_streaming`). Native enables that only for a first-party base URL, so behind the relay a whole-file `write_file` argument arrived in one burst after minutes of silence (live: 89.8 s with no chunk on Opus 5.5) and Hermes' stall timer killed the healthy call.
- Report `Claude request cancelled` when a request is cancelled while native acknowledges replayed history, and include native's exit code and stderr when native exits before that acknowledgment (#122, thanks @Eros-H).
- Restore gzip compression for large direct Anthropic requests, with a process-wide latch and one uncompressed resend when request encoding is rejected.
- A reasoning-off request (`reasoning.enabled: false` or effort `none`) on a route that cannot disable thinking (Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable) now asks for `effort: low` instead of sending no effort, where native thought at its default effort. Routes that accept the disable still receive it.
- Structured output no longer 400s upstream on schema keywords native rejects: `minimum`/`maximum`/`exclusiveMinimum`/`exclusiveMaximum`/`multipleOf` on integer and number, `maxItems`/`uniqueItems` on array, `minProperties`/`maxProperties` on object, and `type` beside `enum` (a nullable enum) are dropped from the wire schema only, and an array `minItems` above 1 is sent as 1. Hermes still validates the reply against the full schema, so the constraints hold, and core no longer retries without a schema (a doubled call).
- Tell the host the request is alive while native streams events that carry no text (tool-call arguments as `input_json_delta`, thinking signatures, block boundaries). Hermes' stale detector only sees chunks, so a long tool call used to look like a stall and the host cancelled a healthy request at its stale budget, then replayed it (#35). Each such event now yields a content-free chunk; pings do not, since they show an open connection and not model work. Final responses are unchanged.
- Keep one native session per conversation (`--session-id` from the system prompt and first frame): with feature flags on, native names a per-session scratchpad directory in the environment message after the first user turn, so a new session per spawn changed it on every request and each round re-wrote the conversation to the prompt cache.
- Short model names such as `sonnet-5-5`, `sonnet-5.5`, `opus-4.8` and `haiku-4-5` resolve to their pinned routes (and thinking policy) instead of reaching Claude Code verbatim and 404ing into the fallback chain (#103).
- `/usage` asks Claude Code for the plan limits (`get_usage` control request) instead of reading its login: it now works with `auth.adopt_external_logins: false`, follows the per-profile `claude_config_dir`, and the plugin never holds the CLI's token (#82).
- Return completed per-call answers at native's result event while its shutdown drains in the background with a bounded grace period (~0.6 s per request under the default telemetry setting). Only a clean admitted answer takes this path; its exit code is no longer read.
- Accept Hermes tool names of 51–64 characters through stable 50-character aliases, mapping native tool calls back to the original names and preserving replay.
- Accept Hermes Relay's host-local `traceparent` request metadata without forwarding it to the native CLI or upstream, preventing full agent and fallback requests from failing on `extra_headers`.
- Continue rejecting arbitrary headers, credential overrides, and malformed header containers at the transport boundary.
- Carry the login identity Claude Code's local check reads (`USER`/`LOGNAME`, `USERNAME` on Windows) into the child env, derived from the parent process or the running uid: without it a perfectly logged-in CLI reports `loggedIn: false` instantly, with no stderr and no upstream request — the confirmed mechanism behind gateway-only `ClaudeCodeLoggedOut` failures (#44).
- Capture native stderr (bounded, drained off-thread) and include its first lines in `ClaudeCodeLoggedOut` and native-failure errors, so a gateway-only failure is diagnosable instead of vanishing into `DEVNULL` (#44).
- A `ClaudeCodeLoggedOut` error names the Claude Code binary it ran and the login directory that spawn used (its `CLAUDE_CONFIG_DIR`, else its own `HOME`'s `.claude`), so a gateway that resolves a different CLI or login than your shell is visible in the error itself (#47).
